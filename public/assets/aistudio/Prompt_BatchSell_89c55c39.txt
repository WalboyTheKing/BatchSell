# 2. CONTEXTE DU PROBLÈME

J'ai utilisé Binance AI Pro avec Binance Agentic Wallet sur BNB Chain.

Le wallet permet à un agent IA de préparer et d'exécuter des opérations on-chain à partir de commandes en langage naturel.

Le problème apparaît lorsque l'utilisateur veut vendre plusieurs tokens fourMeme, notamment pendant leur phase de marché interne ou de bonding curve.

Selon le parcours observé :

1. L'utilisateur demande à l'agent de vendre plusieurs tokens.
2. L'agent prépare les appels nécessaires pour chaque token.
3. Chaque token peut nécessiter une autorisation ERC-20 distincte.
4. Le wallet demande des confirmations successives.
5. L'utilisateur doit répéter les opérations manuellement.

Pour un portefeuille contenant de nombreux tokens, cette expérience devient longue et pénible.

Le problème à résoudre est la granularité excessive des confirmations et l'absence éventuelle d'un mécanisme de batching adapté.

Le but n'est PAS de supprimer les protections du wallet.

Le but est de regrouper les opérations compatibles, de présenter toutes les conséquences à l'utilisateur et de réduire le nombre de transactions et de confirmations lorsque la technologie le permet.

Les mécanismes exacts de vente et d'autorisation doivent être vérifiés à partir de la documentation et des contrats officiels. Ne considère pas les observations ci-dessus comme une preuve que tous les tokens fourMeme fonctionnent de manière identique.

# 3. VISION DU PRODUIT

Nom du projet : BatchSell.

Nom descriptif : Agentic Wallet Transaction Batching Infrastructure.

Positionnement :

« Préparer, vérifier et exécuter plusieurs opérations on-chain à partir d'un plan transparent, avec un minimum de transactions et de confirmations, sans sacrifier le contrôle de l'utilisateur. »

Le premier cas d'utilisation est la vente groupée de tokens fourMeme sur BNB Chain.

L'architecture doit permettre d'ajouter ultérieurement d'autres protocoles et d'autres types d'opérations.

Le produit doit être indépendant du wallet dans sa conception.

Binance Agentic Wallet constitue une intégration cible, mais le développement ne doit pas dépendre d'une API Binance non vérifiée.

---

# 4. OBJECTIFS FONCTIONNELS

Le produit doit permettre à un utilisateur de :

1. Connecter un wallet compatible.
2. Consulter les tokens ERC-20 détenus sur BNB Chain.
3. Identifier les tokens compatibles avec le protocole pris en charge.
4. Sélectionner plusieurs tokens.
5. Définir les quantités à vendre.
6. Consulter les allowances existantes.
7. Identifier les autorisations supplémentaires nécessaires.
8. Construire un plan d'exécution groupé.
9. Simuler les opérations avant leur envoi.
10. Consulter les montants estimés, les frais et les risques.
11. Vérifier chaque opération individuellement.
12. Confirmer le plan complet.
13. Exécuter les opérations avec le mécanisme compatible avec le wallet.
14. Consulter le résultat de chaque opération.
15. Vérifier les reçus de transaction et les soldes après exécution.

Le système doit réduire le nombre d'interactions lorsque c'est techniquement possible.

Il ne doit jamais promettre une signature unique si le wallet, le protocole ou les contraintes EVM rendent cela impossible.

## 5.1. Architecture de fourMeme

À partir des sources officielles disponibles, identifie :

- Les frais et mécanismes de slippage.

Pour chaque information importante, indique la source et la méthode de vérification.

Si les informations nécessaires ne sont pas accessibles, indique précisément ce qui manque.

N'invente aucune adresse de contrat.

N'utilise pas une adresse provenant d'un tutoriel non officiel sans vérification indépendante.

## 5.2. Analyse du problème Multicall

Explique et teste le comportement de `msg.sender` lors des appels à travers Multicall3.

Vérifie si les contrats ERC-20 voient :

- Le compte de l'utilisateur.
- Le contrat Multicall.
- Un autre contrat intermédiaire.

Démontre pourquoi le mécanisme choisi permet ou ne permet pas d'effectuer les autorisations nécessaires.

Ne suppose pas que Multicall3 résout automatiquement le problème.

## 5.3. Analyse EIP-7702

Vérifie :

- Le support du mécanisme sur le réseau ciblé.
- Les exigences des transactions de délégation.
- Le fonctionnement du code délégué.
- Les possibilités de batching.
- Les implications de sécurité.
- Les mécanismes de révocation.
- Les autorisations ERC-20 persistantes.
- Les coûts de gas.
- Les limites de compatibilité des wallets.

Distingue clairement le support d'EIP-7702 par la blockchain du support de cette fonctionnalité par un wallet particulier.

## 5.4. Compatibilité Binance Agentic Wallet

Consulte les documentations officielles disponibles pour Binance Agentic Wallet et Binance AI Pro.

Vérifie l'existence et la disponibilité réelle de :

- Connecteurs wallet.
- Interfaces de signature.
- API de soumission de transactions.
- Prise en charge d'EIP-7702.
- Mécanismes de transaction groupée.
- SDK ou outils destinés aux développeurs.

N'invente pas de méthode, de package, de SDK ou d'endpoint.

Si une intégration directe n'est pas possible avec les interfaces accessibles, crée une architecture d'adaptation et documente les limites.

L'utilisateur ne doit jamais avoir à communiquer sa clé privée ou sa phrase de récupération à l'application.

## 5.5. Décision technique

À la fin de l'audit, compare au minimum :

A. Transactions ERC-20 classiques.

B. Batching via un contrat executor.

C. EIP-7702 avec code de délégation.

D. Mécanisme de compte intelligent compatible, si pertinent.

Pour chaque solution, compare :

- Nombre de transactions.
- Nombre de signatures ou confirmations.
- Coût du gas.
- Compatibilité avec les tokens.
- Compatibilité avec les wallets.
- Complexité de développement.
- Risques de sécurité.
- Facilité de révocation.
- Possibilité d'exécution atomique.

Choisis la solution la plus adaptée au MVP.

Ne choisis pas EIP-7702 uniquement parce qu'il s'agit de la technologie la plus récente.

# 12. APPROVAL ENGINE

Développe un module de gestion des allowances ERC-20.

Règles obligatoires :

- Ne pas demander une autorisation illimitée par défaut.
- Vérifier l'allowance existante avant de proposer une nouvelle autorisation.
- Calculer le montant nécessaire.
- Vérifier le contrat destinataire.
- Afficher le montant et la durée effective de l'autorisation.
- Expliquer si l'autorisation restera active après la vente.
- Prévoir un moyen de réduire ou révoquer les allowances lorsque cela est possible.

L'approbation de plusieurs tokens ne doit être regroupée que si le mécanisme retenu permet réellement de modifier leurs allowances au nom du compte approprié.

# 13. BATCH EXECUTOR : CONTRAT INTELLIGENT

Après l'audit de faisabilité, développe un contrat executor uniquement si cette architecture apporte un avantage réel.

Si EIP-7702 est retenu, le code doit être conçu pour être utilisé dans le cadre exact du mécanisme de délégation et des transactions compatibles.

Ne confonds pas un contrat executor classique avec le code délégué d'un compte EIP-7702.

Le contrat ou code délégué doit respecter les exigences suivantes.

## Contrôles

- Destinations autorisées.
- Fonctions autorisées.
- Limites de taille des batches.
- Limites de montants.
- Validation des paramètres.
- Contrôle des appels externes.
- Gestion des échecs.
- Événements permettant l'audit.
- Protection contre les réentrances lorsque pertinente.
- Protection contre les appels arbitraires.
- Absence de fonction de retrait permettant à un tiers de récupérer les fonds de l'utilisateur.

## Exécution

Le système doit permettre de définir une liste explicite d'opérations.

Chaque opération doit contenir :

- Destination.
- Données d'appel.
- Valeur native éventuelle.
- Limites de sécurité.
- Politique d'échec.

L'exécuteur ne doit pas accepter des appels arbitraires provenant d'une API non fiable.

Le frontend ne doit pas constituer l'unique couche de sécurité.

## Atomicité

Le mode par défaut doit être atomique lorsque le mécanisme retenu le permet :

Si une opération échoue, la transaction complète est annulée.

Si un mode d'exécution partielle est développé, il doit être distinct, explicite et testé.

## EIP-7702

Si la délégation est retenue :

- Documente précisément le mécanisme.
- Explique comment la délégation est autorisée.
- Identifie les limites de contrôle et de révocation.
- Traite les risques liés au stockage et aux appels du code délégué.
- Vérifie la compatibilité de chaque wallet pris en charge.
- Ne promets pas une seule signature sans preuve expérimentale.

Si le mécanisme n'est pas suffisamment maîtrisé ou testé, ne déploie pas de contrat de production.
